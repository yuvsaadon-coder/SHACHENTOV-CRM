# ארכיון אשכולות העשור הבא

מערכת פנימית לתיוק החומרים המקצועיים של תוכנית "אשכולות העשור הבא", ובה שלושה חלקים:

1. **סקיל תיוק ל-Claude** (`skill/ashkolot-filing.zip`). כל חבר/ת צוות שולח/ת מסמך, או תיקייה שלמה, ל-Claude. הסקיל מציע תיקייה, תגיות, כותרת, תקציר וקישורים, ומציג **נימוק וראיה מהמסמך לכל החלטה**. רק אחרי אישור הוא מפיק "כרטיס תיוק" או מבצע את התיוק. הסקיל כולל את **כללי המיפוי** (`references/mapping-rules.md`) ואת **התקדימים**: איך מופה החומר הקיים ולמה. כך כולם מתייקים באותה שיטה, בצורה שקופה.
2. **אתר הארכיון** (`app/`). כאן מעלים את הקובץ ומדביקים את הכרטיס. באתר אפשר לחפש, לסנן לפי כל ציר, לראות קישורים וגרסאות, לתייק מחדש ולנהל את מבנה התיוק.
3. **שכבת אבטחה** (`firebase/`). כללי Firestore ו-Storage נאכפים בשרת, ואי אפשר לעקוף אותם מהדפדפן.

| עיקרון | מקור | איך מיושם |
|---|---|---|

| מזהה ייחודי וקבוע לכל רשומה | ISO 15489 (ניהול רשומות) | `AK-###`, שמוקצה בשרת ולא משתנה בתיוק מחדש. מופיע בשם הקובץ בהורדה, בחיפוש ובקישורים. |
| סיווג לפי פונקציה, לא לפי נושא | ISO 15489 | התיקייה נקבעת לפי תפקיד המסמך בשרשרת: אבחון ← כיוון ← מתחים ← המלצות ← מסמך סופי. |

| מטא-דאטה של מחבר, תאריך ויחסים | Dublin Core / ISO 23081 | שדה מחבר/ת נפרד מהמעלה/ה, וקשרים מסוג נגזר מ / מצטט / נדון במפגש / מזין. |
| גרסאות ויומן ביקורת | ניהול רשומות | משפחות גרסאות, ויומן היסטוריה שאי אפשר לשנות, כולל **נימוק התיוק**. |
| שקיפות ואישור | דרישת הצוות | כל הצעה מגיעה עם נימוק וראיה, ושום דבר לא מתויק בלי אישור. |

## מבנה התיוק

תשע תיקיות לפי **תפקיד המסמך בתהליך**. כל שאר החיתוכים הם תגיות.

שני **אזורים נפרדים**, שכללי האבטחה אוכפים: חומר חיצוני לא נכנס לתוצרי הצוות, ותוצר של הצוות לא נכנס לחומרים החיצוניים.

**א. תוצרי הצוות**

| תיקייה | מה נכנס |
|---|---|
| 01 מסגרת ומתודולוגיה | מדריכים, תבניות, מבנה המסמך הסופי, מילון מונחים |
| 03 נתונים וכלי איסוף של הצוות | נתונים, ניתוחים כמותיים וכלי איסוף שהצוות בנה |
| 04 אבחון | SWOT, ניתוח מצב קיים, יכולות דינמיות, סקירות של הצוותים |
| 05 כיוון | SOAR, תמונת עתיד, עקרונות וערכים |
| 06 מתחים וסוגיות להכרעה | מפות מתחים, מרשם שאלות פתוחות, הצלבות |
| 07 המלצות | כרטיסי המלצה וחלופות |
| 08 תוצר מדיניות | טיוטות המסמך הסופי (24 פרקים) |
| 09 מפגשים | חומרי הכנה וסיכומים, לכל פורום, לפי תאריך |

**ב. חומרים חיצוניים** (כולל החומרים שנאספו לאתר)

| תיקייה | מה נכנס |
|---|---|
| 02.1 ממשלה ורגולציה | משרד הפנים, מבקר המדינה, הכנסת, מנהל התכנון, חקיקה ונהלים |
| 02.2 בינלאומי | OECD וסקירות השוואתיות |
| 02.3 מחקר וחשיבה | ג'וינט-אלכא, סקירות ידע, מכוני מחקר, אקדמיה |
| 02.4 מהשטח | חומרים שהפיקו אשכולות ספציפיים |
| 02.5 נתונים | קובצי נתונים שהתקבלו מגורם חיצוני |

**הקבצים לא נערכים:** הארכיון שומר כל קובץ בדיוק כפי שהועלה:
- בלי לשנות תוכן, עיצוב, פורמט או שם, ובלי המרה.
- הכותרת, המזהה והתגיות הם מידע נלווה בלבד.
- בהורדה מקבלים את הקובץ המקורי בשמו המקורי.
- שלמות הקובץ נבדקת ב-SHA-256. בייבוא נבדק גם MD5 מול הקובץ שנשמר, וקובץ שלא זהה למקור לא נשמר.

**תגיות:**
- פורום
- ממד: ניהול / תכנון / פיתוח (ו"מנגנון", שעדיין לא הוכרע)
- אחריות: ממשלה / אשכול / רשויות
- יחידת ניתוח
- רגל: תמך מוניציפלי / פיתוח אזורי
- תחום תוכן
- מעגל בעלי עניין
- פרק במסמך הסופי
- סוג מסמך
- סטטוס
- גוף מפרסם

**קישורים:**
- נגזר מ
- מצטט מקור
- נדון במפגש
- מזין את
- מגיב ל
- קשור ל

**גרסאות:** כל גרסה היא רשומה נפרדת במשפחת גרסאות. רק הגרסה הנוכחית מוצגת כברירת מחדל.

מקור האמת של המבנה הוא `taxonomy/taxonomy.json`. אחרי ההתקנה, המבנה נערך מתוך האתר (ניהול ← מבנה התיוק). אפשר לשנות תוויות, להוסיף ערכים ולהשבית ערכים. **אי אפשר למחוק ערך**, כדי שמסמכים קיימים יישארו תקינים. הכלל הזה נאכף גם בשרת.

## התקנה (פעם אחת, בלי שורת פקודה)

### 1. פרויקט Firebase
- **יצירה:** https://console.firebase.google.com/ ← Create a project ← `ashkolot-archive`
- **כניסה עם Google:** Authentication ← Sign-in method ← Google ← Enable
- **Firestore:** Firestore Database ← Create database ← europe-west1 ← Production mode
- **Storage:** Storage ← Get started. נדרשת תוכנית Blaze, העלות זניחה, ומומלץ להגדיר התראת תקציב.
- **פרטי חיבור:** Project settings ← Your apps ← `</>`. שומרים את הערכים של `firebaseConfig`.

### 2. כללי האבטחה (העתק-הדבק)
- **Firestore:** Firestore ← Rules. מדביקים את כל התוכן של `firebase/firestore.rules` ולוחצים Publish.
- **Storage:** Storage ← Rules. מדביקים את `firebase/storage.rules` ולוחצים Publish. כשמתבקשים לאשר גישה של Storage ל-Firestore, מאשרים.

### 3. האתר ב-Netlify
1. https://app.netlify.com/start ← GitHub ← הריפו הזה.
2. **Base directory:** `ashkolot-archive/app`. שאר ההגדרות נקראות מ-`app/netlify.toml`.
3. **Environment variables:** מוסיפים את ערכי `firebaseConfig`:
   - `VITE_FIREBASE_API_KEY`
   - `VITE_FIREBASE_AUTH_DOMAIN`
   - `VITE_FIREBASE_PROJECT_ID`
   - `VITE_FIREBASE_STORAGE_BUCKET`
   - `VITE_FIREBASE_APP_ID`
4. **Deploy.**
5. **הרשאת הדומיין:** ב-Firebase, Authentication ← Settings ← Authorized domains ← מוסיפים את כתובת האתר של Netlify.

### 4. כניסה ראשונה וייבוא
- **הגדרה ראשונית:** נכנסים לאתר עם חשבון ה-Google שלכם. כשהמערכת ריקה מופיע מסך "הגדרה ראשונית", ולחיצה אחת יוצרת את מבנה התיוק ומגדירה אתכם כמנהל/ת. האפשרות קיימת רק כשהארכיון ריק, אז כדאי לעשות זאת מיד אחרי הפריסה.
- **ייבוא החומר הקיים:** ניהול ← ייבוא החומר הקיים ← בוחרים את התיקייה עם הקבצים. האתר מציג מה ייובא ולאן, ואחרי אישור מייבא עם המזהים (`AK-###`) והנימוקים מהקטלוג. הקבצים נשמרים כפי שהם. אפשר להריץ שוב: מה שכבר בארכיון מדולג.
- **משתמשים:** ניהול ← משתמשים והרשאות.

> **חלופה למי שמעדיף שורת פקודה:** `firebase deploy` וסקריפטי `npm run setup` / `npm run import-archive` עדיין קיימים ועובדים (ראו `app/scripts`).

### 5. הפצת הסקיל לצוות
- **לפני שהאתר פעיל:** `skill/ashkolot-filing.zip`, שנבנה מהקטלוג הראשוני.
- **אחרי שהאתר פעיל:** ניהול ← סקיל וייצוא ← **הורדת סקיל מעודכן**. הגרסה הזו כוללת את מבנה התיוק הנוכחי ואת רשימת המסמכים בארכיון, בלי מסמכים "לא להפצה".
- **התקנה אצל כל אחד/ת:** Claude ← Settings ← Capabilities ← Skills ← Upload skill.
- **מתי לעדכן:** אחרי כל שינוי במבנה התיוק, ומדי פעם כדי לרענן את רשימת המסמכים שהסקיל מכיר.

## עבודה שוטפת

**תיוק מסמך חדש:**
1. שולחים את הקובץ ל-Claude ("תתייק לי את זה").
2. Claude מציע תיוק. מאשרים או מתקנים.
3. Claude מפיק כרטיס תיוק.
4. באתר: **העלאה** ← גוררים את הקובץ ← מדביקים את הכרטיס ← **מילוי** ← בודקים ← **שמירה**.

**גרסה חדשה של מסמך קיים:** פותחים את המסמך ← **העלאת גרסה חדשה**. התיוק עובר מהגרסה הקודמת, והקודמת נשמרת בהיסטוריה.

**תיוק מחדש:** פותחים את המסמך ← **עריכה / תיוק מחדש**. אפשר גם להדביק כרטיס חדש מהסקיל. כל שינוי נרשם ביומן, עם מי, מתי ומה השתנה.

**כפילויות:** בהעלאה, האתר מחשב טביעת אצבע (SHA-256) ומזהיר אם קובץ זהה כבר קיים.

**גיבוי:** ניהול ← סקיל וייצוא ← **הורדת CSV** של כל הקטלוג. לגיבוי מלא של Firestore אפשר להגדיר ייצוא מתוזמן ב-Google Cloud.

שתי הפקודות האחרונות מריצות את האתר מקומית מול אמולטורים, עם כניסת פיתוח, בלי פרויקט אמיתי. מריצים אותן בשני חלונות נפרדים.

> בסביבה עם proxy ארגוני, האמולטורים צריכים לרוץ בלי `HTTPS_PROXY`. אחרת הגישה של Storage ל-Firestore בתוך האמולטור נכשלת.

**כדי שהמערכת תישאר עקבית:**
- כל שדה חדש במסמך דורש עדכון בשלושה מקומות: `model.ts` (טיפוס ואימות), `firestore.rules` (רשימת שדות ואימות), והתבנית ב-`SKILL.md`.
- הבדיקות ב-`test/unit` מוודאות שהסקיל והמבנה מסונכרנים.
