# ארכיון אשכולות העשור הבא

מערכת פנימית לתיוק החומרים המקצועיים של תוכנית "אשכולות העשור הבא", ובה שלושה חלקים:

1. **סקיל תיוק ל-Claude** (`skill/ashkolot-filing.zip`). כל חבר/ת צוות שולח/ת מסמך, או תיקייה שלמה, ל-Claude. הסקיל מציע תיקייה, תגיות, כותרת, תקציר וקישורים, ומציג **נימוק וראיה מהמסמך לכל החלטה**. רק אחרי אישור הוא מפיק "כרטיס תיוק" או מבצע את התיוק. הסקיל כולל את **כללי המיפוי** (`references/mapping-rules.md`) ואת **התקדימים**: איך מופה החומר הקיים ולמה. כך כולם מתייקים באותה שיטה, בצורה שקופה.
2. **אתר הארכיון** (`app/`). כאן מעלים את הקובץ ומדביקים את הכרטיס. באתר אפשר לחפש, לסנן לפי כל ציר, לראות קישורים וגרסאות, לתייק מחדש ולנהל את מבנה התיוק.
3. **שכבת אבטחה** (`firebase/`). כללי Firestore ו-Storage נאכפים בשרת, ואי אפשר לעקוף אותם מהדפדפן.

| שקיפות ואישור | דרישת הצוות | כל הצעה מגיעה עם נימוק וראיה, ושום דבר לא מתויק בלי אישור. |

## התקנה (פעם אחת, כ-30 דקות)

### 1. פרויקט Firebase
1. ב-[console.firebase.google.com](https://console.firebase.google.com) צרו פרויקט חדש, למשל `ashkolot-archive`. מומלץ פרויקט נפרד מה-CRM.
2. **Build ← Authentication ← Sign-in method:** הפעילו **Google**. אם הצוות משתמש בחשבונות Microsoft, הפעילו גם **Microsoft** (דורש רישום אפליקציה ב-Azure).
3. **Build ← Firestore Database:** צרו מסד נתונים במצב Production, באזור `europe-west1` או קרוב.
4. **Build ← Storage:** הפעילו. Storage דורש תוכנית **Blaze**. בהיקף של כמה מאות MB העלות זניחה (סנטים בחודש). מומלץ להגדיר התראת תקציב.
5. **Project settings ← Your apps:** הוסיפו אפליקציית Web והעתיקו את הערכים לקובץ `app/.env.local` (לפי `app/.env.example`).

### 2. פריסת כללי האבטחה והאתר
מתוך תיקיית `ashkolot-archive`:

```bash
cp .firebaserc.example .firebaserc
```

ערכו את `.firebaserc` והכניסו את מזהה הפרויקט. אחר כך:

```bash
cd app && npm install && npm run build && cd ..
```

```bash
npx --prefix app firebase login
```

```bash
npx --prefix app firebase deploy --only firestore,storage,hosting
```

בפריסה הראשונה, Firebase יבקש לאשר ש-Storage ניגש ל-Firestore. כללי הקבצים צריכים את הגישה הזו כדי לבדוק הרשאות, אז אשרו.

### 3. מנהל/ת ראשון/ה ומבנה התיוק
1. הורידו מפתח חשבון שירות: Project settings ← Service accounts ← Generate new private key. שמרו אותו **מחוץ לריפו**.
2. הריצו:

```bash
export GOOGLE_APPLICATION_CREDENTIALS=~/keys/ashkolot-sa.json
```

```bash
cd app && npm run setup -- --project <project-id> --admin your@email.org
```

3. היכנסו לאתר (`https://<project-id>.web.app`) והוסיפו את חברי הצוות ב**ניהול ← משתמשים והרשאות**.

### 4. ייבוא החומר הקיים
`seed/catalog.json` מכיל סיווג של **99 מסמכים** מתיקיית ה-Drive ומסיכומי המפגשים. הסיווג נעשה לפי **תוכן** הקבצים: עמוד שער, כותרות ותאריכים.
- לכל מסמך: מזהה `AK-###`, כותרת מלאה, גוף מפרסם, מחבר/ת היכן שכתוב, ו**נימוק**.
- 6 כפילויות אוחדו.
- 12 רשומות נשארו "לאימות", עם הסבר מה בדיוק לבדוק.

**הצעת התיוק ב-Drive:** הצעה שורה-שורה לכל 116 הקבצים נמצאת בגיליון "הצעת תיוק – לאישור", בתיקייה "ארכיון אשכולות – מתויק". כל שורה כוללת שם נוכחי, שם חדש, תיקייה ונימוק. **התיוק ב-Drive יבוצע רק אחרי אישור.**

1. הורידו את תיקיית ה-Drive כ-zip ופרסו אותה לתיקייה מקומית. העתיקו לאותה תיקייה גם את 7 קובצי סיכומי המפגשים.
2. הרצה יבשה, שבודקת התאמה ולא כותבת דבר:

```bash
npm run import-archive -- --project <project-id> --dir ~/Downloads/ashkolot --as your@email.org --dry-run
```

3. ייבוא בפועל:

```bash
npm run import-archive -- --project <project-id> --dir ~/Downloads/ashkolot --as your@email.org
```

אפשר להריץ את הייבוא שוב בבטחה. קבצים שכבר יובאו מזוהים לפי SHA-256 ומדולגים, וקישורים ומשפחות גרסאות מתחברים גם בין הרצות.
4. באתר, חפשו **"לאימות"** ועברו על הרשומות המסומנות. לכל רשומה: עריכה ← תיקון ← שמירה.

### 5. הפצת הסקיל לצוות
- **לפני שהאתר פעיל:** `skill/ashkolot-filing.zip`, שנבנה מהקטלוג הראשוני.
- **אחרי שהאתר פעיל:** ניהול ← סקיל וייצוא ← **הורדת סקיל מעודכן**. הגרסה הזו כוללת את מבנה התיוק הנוכחי ואת רשימת המסמכים בארכיון, בלי מסמכים "לא להפצה".
- **התקנה אצל כל אחד/ת:** Claude ← Settings ← Capabilities ← Skills ← Upload skill.
- **מתי לעדכן:** אחרי כל שינוי במבנה התיוק, ומדי פעם כדי לרענן את רשימת המסמכים שהסקיל מכיר.

## עבודה שוטפת

**תיוק מסמך חדש:**
1. שולחים את הקובץ ל-Claude ("תתייק לי את זה").
2. Claude מציע תיוק. מאשרים או מתקנים.
3. Claude מפיק כרטיס תיוק.
4. באתר: **העלאה** ← גוררים את הקובץ ← מדביקים את הכרטיס ← **מילוי** ← בודקים ← **שמירה**.

**גרסה חדשה של מסמך קיים:** פותחים את המסמך ← **העלאת גרסה חדשה**. התיוק עובר מהגרסה הקודמת, והקודמת נשמרת בהיסטוריה.

**תיוק מחדש:** פותחים את המסמך ← **עריכה / תיוק מחדש**. אפשר גם להדביק כרטיס חדש מהסקיל. כל שינוי נרשם ביומן, עם מי, מתי ומה השתנה.

**כפילויות:** בהעלאה, האתר מחשב טביעת אצבע (SHA-256) ומזהיר אם קובץ זהה כבר קיים.

**גיבוי:** ניהול ← סקיל וייצוא ← **הורדת CSV** של כל הקטלוג. לגיבוי מלא של Firestore אפשר להגדיר ייצוא מתוזמן ב-Google Cloud.

שתי הפקודות האחרונות מריצות את האתר מקומית מול אמולטורים, עם כניסת פיתוח, בלי פרויקט אמיתי. מריצים אותן בשני חלונות נפרדים.

> בסביבה עם proxy ארגוני, האמולטורים צריכים לרוץ בלי `HTTPS_PROXY`. אחרת הגישה של Storage ל-Firestore בתוך האמולטור נכשלת.

**כדי שהמערכת תישאר עקבית:**
- כל שדה חדש במסמך דורש עדכון בשלושה מקומות: `model.ts` (טיפוס ואימות), `firestore.rules` (רשימת שדות ואימות), והתבנית ב-`SKILL.md`.
- הבדיקות ב-`test/unit` מוודאות שהסקיל והמבנה מסונכרנים.
