# Requirements-based test design — Shachentov CRM

## 1. Status, authority, and decision rules

**Design only; no tests implemented or executed by this document's author.** Application baseline: `60548f8`. Requirements: the two Hebrew documents under `docs\requirements`. Production evidence below was read in this isolated worktree. Dependency restoration and any subsequent design reviews belong to the parent session. This document does not approve implementation, alter production, establish business policy, or claim deployment verification.

The suite must test the actual React application, exported hooks, components, Netlify `handler` exports, and unchanged Firebase rules. A test-only implementation of filtering, authorization, recurrence, or report aggregation is not an oracle.

Two independent questions must remain visible:

1. **What does the baseline do?** A characterization can pass while documenting an undesirable behavior.
2. **Does it meet a firm requirement?** An acceptance test must remain normally failing when production violates it. Do not use `test.fails`, expected-failure inversion, unconditional skips, retries, relaxed mocks, or assertions that merely prove a feature is absent to make the gate green.

Labels used below:

| Label | Meaning |
|---|---|
| `A` | Firm acceptance behavior; baseline plausibly meets it, subject to execution. |
| `G` | Firm acceptance behavior; code evidence predicts a behavioral gap. Run a normal assertion and report the actual result. |
| `C` | Current-behavior characterization, not approval of policy or implementation. |
| `U` | Unresolved requirement; record a characterization and decision needed, not a guessed acceptance oracle. |
| `I` | Missing test infrastructure prevents execution; not a production assertion failure. |
| `F` | Future runtime feature has no executable production entrypoint yet; retain an explicit coverage gap. |
| `M` | Operational/manual evidence unavailable in this offline environment. |

**Every concrete runtime test has exactly one classification: A, G, or C.** U/F/M are non-runnable requirement/evidence dispositions, never an invented runtime oracle; I is an execution status, never a test classification. Family summaries may list multiple dispositions, but they are not concrete tests. The explicit subcase registry in section 6.1 overrides family shorthand and separates each oracle. A prediction is not a confirmed defect. A real failure requires the independent verification process in section 9.

### Owner clarifications incorporated before design review

- [Executive L77](..\..\docs\requirements\executive-summary.he.md#L77) requires task-based AI answers even though technical scopes omit tasks. H05 must verify actual task facts reach the answer context; it must **not** prescribe a new scope name or selector design.

H06/Q04 use the explicitly seeded existing branches A/B/C/D as their population. Production eligibility rules (inactive, newly opened or otherwise exempt branches) remain unresolved.
- [Executive L81](..\..\docs\requirements\executive-summary.he.md#L81) makes personal tasks private from **all other users, including admin**. General “admin sees all information” wording does not create an exception; S07 explicitly denies another user's private-task access to admin.
- [Executive L73](..\..\docs\requirements\executive-summary.he.md#L73) explicitly requires knowledge domain/category/tag filtering; K01/K02/K04 and A03 cover these without selecting the disputed storage model. [Executive L85](..\..\docs\requirements\executive-summary.he.md#L85) explicitly requires contact type/department filtering; C01/C02 cover both, independently of unresolved server-side domain visibility.

The 99 rows above are **families**, not 99 executable tests. This registry is mandatory for every mixed family and the corrected integration journeys. Each entry below names a concrete suffix and **one** classification in parentheses. Family GIVEN values, WHEN steps, requirements and P citations are inherited only where relevant to that suffix. ### Browser assertion discipline

Use scoped accessible roles/names: locate the intended dialog/form/region first, then its named textbox, button, combobox or row. ## 7. Practical grouping and prioritization

There are **99 logical scenario families** above, including non-runnable future/manual/policy evidence specifications. This is not an arbitrary cap and not the eventual `it` count. Section 6.1's classified concrete registry is authoritative. Expanded route, function, hook and rules matrices receive stable suffixes, for example `F01.portal-login.malformed-json`, `S04.foreign-branch`, `L02.useContacts.denied`. Each runnable `it`/Playwright test has exactly one stable ID, one A/G/C classification and one independent outcome verifier; I is recorded only as run status.

Implementation order after design approval:

1. **Safety and discoverability**: isolated configs, real-demo emulators, fail-closed egress, fixture cleanup, exact test manifest. Prove safety bootstrap with no application data.
2. **Core behavioral cases**: identity/routes, task writer-reader, private tasks, contact CRUD, report submission/coverage, real handler contracts. Keep genuinely failing acceptance separate from successful characterizations.
3. **Emulator boundaries and persistence**: all rules matrices, real undefined-field rejection, Storage operations, custom-token flow, denormalized partial failures and concurrent writes.
4. **Knowledge/AI source fidelity and branch transitions**: real UI→handler→provider payload capture, report mismatch, mirror deletion, static catalog divergence, history/session races.
5. **Cross-persona browser/recovery/accessibility**: full journeys, focus/RTL and reconnect with actual consumers. Then measurement/operational review; no unapproved external targets.

Do not combine independent failure classes into one enormous `it`. A successful create/edit/filter/delete lifecycle is sensible together; missing auth, malformed JSON and wrong method are separate named cases because each needs an independent verdict. Within a matrix, each resource/role decision that asserts a distinct boundary must be individually listed in results. The parent may split rows further without weakening the ledger.

## 9. Per-test independent verification and defect explanations

The parent runs design review **before implementation**. This author launches no review agents. Once implementation is approved:

1. Generate a manifest of every discovered `it`/`test` name, stable scenario suffix, requirement IDs, production entrypoint, fixture seed, layer and exact targeted command. Compare discovered versus planned runnable tests; undetected tests are infrastructure gaps.
2. Run each exact test from clean isolated state. Capture sanitized assertion output, relevant actual SDK request/persisted records/provider request fragments, and code/requirement citations. A failing setup means **not executed**, not “requirement failed.”
3. Assign **a distinct independent agent per concrete test outcome**. The verifier receives the exact requirement, test and production paths, reproduction command and output—not just the author's verdict. It reruns/inspects that test and checks oracle validity, mocks, source exercised, fixture isolation, actual versus expected outcome, and whether test code itself caused failure. Even passing tests need validation against false positives.
4. Verifier returns: stable test ID; requirement/source citations; executed command/result; actual versus required result; `pass`, `confirmed production defect`, `test defect`, `infrastructure blocked`, `policy unresolved`, `future feature absent`, or `manual evidence unavailable`; and rationale. It must not fix production or change an oracle to fit baseline during outcome review.
5. For **each genuine code defect**, write a concise explanation: requirement violated; smallest synthetic reproduction; causal chain through production lines; observable impact; why mock/test/environment error is excluded; related tests; unresolved policy boundaries; and any directly related consistency risk. Consolidate duplicate root causes only after retaining every test's verdict and evidence.
6. A failed acceptance stays red. A valid characterization may pass while linked acceptance stays red. Do not report a green suite by excluding all gaps. Future jobs with no callable code and approved-policy-dependent oracles stay in the unimplemented/blocked ledger rather than throwing fake imports or asserting missing files.
7. Re-run affected tests after any later authorized fix, plus adjacent writer/reader/rules paths. Full final gates are governed by the parent's reviewed automation proposal; preserve logs and reported nonzero status.

- Only this test-plan file is authored by this task; no tests, production changes, dependency changes, installation, builds or review agents.
- Both Hebrew requirements have exact-line clause mappings, all technical sections and executive features have explicit planned disposition, and every function/hook/module has a production entrypoint.
